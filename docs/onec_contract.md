# Контракт интеграции с 1С (HTTP-сервис)

Документ для команды 1С. Описывает, какие данные и в каком виде внешний сервис
аналитики продаж ожидает получать из 1С. Интеграция **read-only**: сервис только
читает, ничего в 1С не пишет.

## 1. Что нужно от 1С

Один **HTTP-сервис** (или OData-эндпоинт), отдающий **историю позиций заказов** —
по одной записи на строку документа «Заказ покупателя». Сервис аналитики тянет это
**полной выгрузкой по расписанию** (объём порядка 2 млн строк), агрегирует у себя.

Грейн записи: `(документ-заказ) × (строка-номенклатура)`.

## 2. Поля записи

| Поле в ответе | Тип | Источник в 1С (предположение) | Обяз. | Назначение |
|---|---|---|---|---|
| `order_guid`   | string (GUID) | `Документ.ЗаказПокупателя.Ссылка` | да | Идентичность заказа |
| `order_num`    | string | `Документ.ЗаказПокупателя.Номер` | да | Отображение / поиск |
| `order_date`   | string (ISO `YYYY-MM-DD`) | `Документ.ЗаказПокупателя.Дата` | да | Хронология, окна |
| `client_guid`  | string (GUID) | `Контрагент.Ссылка` | да | Идентичность клиента |
| `client_name`  | string | `Контрагент.Наименование` | да | Отображение |
| `niche`        | string | **❓ см. вопрос 2** | да | Группировка по нише |
| `n1`           | string \| null | уровень иерархии номенклатуры | нет | Товарный раздел |
| `n2`           | string \| null | уровень иерархии номенклатуры | нет | Товарная группа |
| `n3`           | string | уровень иерархии номенклатуры | да | Товарная подгруппа |
| `n4`           | string | `Номенклатура.Наименование` | да | Товар |
| `item_guid`    | string (GUID) | `Номенклатура.Ссылка` | да | Идентичность товара (ключ к остаткам) |
| `qty`          | number | `Количество` строки | да | Количество, **в тоннах** (см. вопрос 4) |

> Ключи — **GUID**, а не наименования. Имена меняются и дублируются; вся идентичность
> (клиент, товар, заказ) строится на `Ссылка`. Наименования передаются отдельно для отображения.

### Пример ответа

```json
{
  "items": [
    {
      "order_guid": "a1b2c3d4-0000-0000-0000-000000000001",
      "order_num": "ЗП-0001234",
      "order_date": "2026-03-14",
      "client_guid": "c0ffee00-0000-0000-0000-000000000abc",
      "client_name": "ООО Стройметалл",
      "niche": "Строительство",
      "n1": "01. Металлопрокат",
      "n2": "01.02. Сортовой прокат",
      "n3": "01.02.03. Арматура",
      "n4": "Арматура А500С 12мм",
      "item_guid": "f00d0000-0000-0000-0000-000000000def",
      "qty": 5.4
    }
  ],
  "next_cursor": "eyJsYXN0X2lkIjogMTAwMH0=",
  "total": 2000000
}
```

## 3. Пагинация, авторизация, транспорт

- **Пагинация обязательна** — 2 млн строк в одном ответе недопустимы. Любой из вариантов:
  - курсор (`?cursor=...`, в ответе `next_cursor`, null в конце) — **предпочтительно**, устойчив к вставкам;
  - либо `?top=N&skip=M` (OData-стиль).
- **Стабильный порядок** записей между страницами (по `order_date, order_guid, line`) — иначе пропуски/дубли.
- **TLS** обязателен; сертификат валидный (сервис проверяет).
- **Авторизация:** служебный пользователь 1С с правами **только на чтение** нужных объектов.
  Способ — Basic/токен в заголовке (уточнить, что поддерживает публикация).
- Желательный (не на старте) параметр **инкремента**: `?changed_since=YYYY-MM-DDTHH:MM:SS`
  для дельта-выгрузки. На старте достаточно полной выгрузки.

## 4. Остатки (опционально, отдельный ресурс)

Если остатки тянем из 1С (а не ручным файлом) — отдельный эндпоинт, ключ — `item_guid`:

| Поле | Тип | Источник |
|---|---|---|
| `item_guid`   | string (GUID) | `Номенклатура.Ссылка` |
| `n4`          | string | наименование (для сверки) |
| `on_stock`    | number \| null | остаток, тн (регистр остатков) |
| `in_transit`  | number \| null | в пути, тн (товары в пути) |

## 5. Открытые вопросы к стороне 1С (блокируют финализацию)

1. **Ключи GUID.** Подтвердить, что сервис отдаёт `Ссылка` для контрагента, номенклатуры и заказа,
   а не только наименования.
2. **Ниша (`niche`).** Это **не типовое поле**. Где она живёт — реквизит `Контрагента`, отдельный
   справочник-классификатор, иное? Если в 1С её нет в чистом виде — это нужно завести на стороне 1С,
   иначе анализ по нише невозможен. **Риск №1.**
3. **Иерархия N1–N4.** Как представлена — папки справочника `Номенклатура` (Родитель→Родитель),
   отдельный классификатор или реквизиты-уровни? От этого зависит формирование четырёх полей.
4. **Единица измерения `qty`.** Гарантируется ли передача в **тоннах**? Если в строке базовая ЕИ —
   нужна конверсия на стороне 1С, иначе агрегаты по тоннажу некорректны.
5. **Какие документы включать.** Только **проведённые** заказы? Исключаются ли возвраты/отмены?
   Фильтр по организации/складу нужен?
6. **Семантика даты.** `order_date` — дата заказа или дата отгрузки?
7. **Остатки.** Тянем из 1С (раздел 4) или остаётся ручная загрузка файла «Остатки в выборке»?

## 6. Гарантии со стороны сервиса аналитики

- Только чтение; нагрузка — периодическая полная выгрузка с **ограниченным параллелизмом**
  страниц (не «долбим» боевую базу) и retry/backoff.
- Недоступность 1С не роняет приложение — оно работает на последнем успешно загруженном срезе.
