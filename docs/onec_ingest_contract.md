# Контракт обмена с 1С (push / HTTP)

Документ для команды 1С. **Содержание JSON задаёт сервис аналитики** (здесь).
Read-only со стороны сервиса: 1С передаёт данные, сервис ничего в 1С не пишет.

Два вызова:
- **История заказов** — **дельта** (новые/изменённые заказы), управляется 1С
  (`/api/ingest/order-lines` + `commit`). Удалений нет.
- **Анализ заявки** — в реальном времени (`/api/analyze`): клиент + текущие позиции → рекомендации.

История — плоские строки заказов (как в Excel-выгрузке «Результат…»), но **идентичность
по GUID**: клиент → `client_id`, подгруппа → `n3_id`, товар → `n4_id`. Наименования
(`client_name`, `n3_name`, `n4_name`) — только для отображения. Заказ → `ЗаказНомер`;
ниша → `Отрасль`; количество → `Количество` (единица не важна). Точные имена GUID-полей —
по образцу вашего JSON.

Общее: TLS обязателен; тела — **JSON, UTF-8**.

> Остатки в интеграции **не участвуют** — на рекомендации они не влияют; если нужно,
> 1С показывает их оператору сама рядом с возвращёнными товарами.

---

## 0. Резюме для согласования форматов (что нужно от 1С)

**Что реализовать на стороне 1С:**
1. **Выгрузка истории** — дельтой (новые/изменённые заказы; дельтой управляет 1С)
   POST на `/api/ingest/order-lines` пачками, затем `/api/ingest/commit` (§2–§3).
2. **Получение токена** на `/api/auth/token` по выданному секрету, дальше слать его
   в заголовке `Authorization: Bearer <token>` (§1).
3. **Вызов анализа** `/api/analyze` при разборе заявки оператором (§4) — формат запроса/ответа.

**Формат строки истории** (идентичность по GUID; полный формат — в `onec_api.md §2`):
```json
{ "client_id": "<GUID>", "client_name": "Клиент 12", "Отрасль": "04. Металлотрейдеры",
  "ЗаказНомер": "АГAG-212482", "ЗаказДата": "2024-08-11",
  "n3_id": "<GUID>", "n3_name": "02.01.01. Трубы профильные до 120 …",
  "n4_id": "<GUID>", "n4_name": "Труба профильная 40х20х2 Углерод.",
  "Количество": 1.032 }
```
Обязательны: `client_id`, `n3_id`, `n4_id`, `Отрасль`, `ЗаказНомер`, `Количество`.
Для отображения: `client_name`, `n3_name`, `n4_name`, `ЗаказДата`. `N1`/`N2` не нужны.

**Просьба подтвердить:**
- [ ] идентичность по **GUID**: `client_id`, `n3_id` (подгруппа), `n4_id` (товар) =
      `Ссылка` соответствующих объектов 1С; наименования — для отображения;
- [ ] история — **дельта** (новые/изменённые заказы), дельтой управляет 1С; заказ — по
      `ЗаказНомер`. **Удалений нет** (в 1С ничего не удаляется);
- [ ] **при изменении заказа** присылаете заказ **целиком** (все строки) — мы заменяем его позиции;
- [ ] **возвраты/корректировки** — как приходят в дельте (отдельный документ / отрицательное
      `Количество` / признак) и **учитывать ли** их в аналитике;
- [ ] **заказ и ниша** — оставляем `ЗаказНомер` / `Отрасль` (по ним GUID не нужен)? или тоже GUID;
- [ ] точные имена GUID-полей — по **образцу вашего JSON** (сопоставим);
- [ ] готовы получать токен на `/api/auth/token` (секрет передадим по защищённому каналу).

**Что НЕ нужно передавать:** остатки (в интеграции не участвуют), номер/идентификатор
заказа в `/api/analyze`, какие-либо удаления (в 1С ничего не удаляется).

> Семантика — ниже (§1–§6); точные форматы вход/ответ по всем вызовам — в `onec_api.md`.

## 1. Авторизация (запрос токена → JWT)

```
POST /api/auth/token            Content-Type: application/json
{ "client_id": "onec", "client_secret": "<секрет>" }
→ { "access_token": "<JWT>", "token_type": "bearer", "expires_in": 3600, "scope": "ingest" }
```
Далее в каждом вызове: `Authorization: Bearer <access_token>`.
- `client_id`/`client_secret` выдаём мы (разово). Токен живёт `expires_in` сек.
- Право `ingest` — для `/api/ingest/*`; `analyze` — для `/api/analyze`.
- Нет/просрочен токен → `401`; токен без нужного права → `403`.

> auth-`client_id` приложения-интегратора **не путать** с `client_id` контрагента в данных.

## 2. История заказов — `POST /api/ingest/order-lines`

Грейн — **строка заказа (позиция)** `(заказ × товар)`, плоско; идентичность по GUID
(`client_id`, `n3_id`, `n4_id`), наименования — для отображения.
**Формат запроса и полей — `onec_api.md §2`.**

Семантика — **дельта (управляется 1С)**: новые и изменённые заказы (что уже передано
и что изменилось, отслеживает сама 1С). Грейн обновления — **документ-заказ**: при
изменении присылайте **все строки заказа**, сервис заменяет позиции этого `ЗаказНомер`
(upsert по заказу). **Удалений нет** — в 1С ничего не удаляется. Пачка — 1 000–10 000 строк.

## 3. Финализация пачки — `POST /api/ingest/commit`

Вызывается после загрузки пачки — пересобирает аналитические агрегаты (можно не звать:
сервис пересобирает их и по таймеру). Формат — `onec_api.md §3`.

## 4. Анализ заявки — `POST /api/analyze` (scope `analyze`)

**Stateless**: клиент + текущие позиции заявки → рекомендации. Анализ на уровне **N3**.
В заявке товар — по `n4_id` (можно `n3_id`); номер/id самого заказа не нужен (заявка не
сохраняется). **Формат запроса и ответа — `onec_api.md §4`.**

## 5. Ошибки, надёжность

- Коды: `200` ок; `400` некорректное тело / пустая заявка; `401` нет/просрочен токен;
  `403` токен без права; `5xx` — повтор с backoff.
- Ингест истории идемпотентен. Недоступность сервиса не должна ронять 1С.

## 6. Что обеспечивает сторона 1С

1. **История** — **дельта** (новые/изменённые заказы; управляется 1С), пачки + `commit`;
   при изменении — заказ **целиком**; идентичность по GUID (`client_id`/`n3_id`/`n4_id`).
   Удалений нет.
2. **Возвраты/корректировки** — согласовать представление (отдельный документ /
   отрицательное `Количество` / признак) и учитывать ли в аналитике.
