# Контракт приёма данных от 1С (push / HTTP)

Документ для команды 1С. Описывает HTTP-эндпоинты, **в которые 1С отправляет
данные** во внешний сервис аналитики продаж. Интеграция **read-only со стороны
сервиса**: сервис ничего не пишет в 1С — наоборот, 1С пушит данные в сервис.

Это рабочая модель (подтверждена письмом от 22.06.2026): **1С сама передаёт
данные POST-запросами**, сервис их принимает и складывает в свою БД.
Предыдущий вариант (сервис тянет полную выгрузку) — отменён;
см. `docs/onec_contract.md` только как справочник по полям/ключам/нише.

---

## 0. Общая схема

Сервис — это, по сути, два эндпоинта:

1. **Приём истории** — 1С пушит строки заказов и остатки → пишем в БД.
2. **Анализ** — оператор (или 1С) шлёт текущую заявку → получает рекомендации в ответе.

```
1С  ──POST /api/ingest/order-lines──▶  сервис ──▶  БД (сырьё)
1С  ──POST /api/ingest/stock───────▶               │
                                       (по таймеру) ▼
                                     пересчёт аналитики (агрегаты)
оператор/1С ──POST /api/analyze──▶  сервис ──▶  JSON с рекомендациями
```

- Базовый URL: `https://<host>` (TLS обязателен).
- Все тела запросов/ответов — **JSON, UTF-8**.
- Все денежные/весовые величины — числа; **количество в тоннах**.
- Идентичность — **GUID** (`Ссылка` из 1С), не наименования.

## 1. Авторизация (OAuth2 Client Credentials, app-to-app)

Машина-машина. 1С получает токен по своему `client_id` / `client_secret`,
затем шлёт его в заголовке к остальным запросам.

### Получение токена

```
POST /api/auth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=onec&client_secret=<секрет>
```

Ответ:
```json
{ "access_token": "<JWT>", "token_type": "bearer", "expires_in": 3600, "scope": "ingest" }
```

### Использование

Во всех `/api/ingest/*` запросах:
```
Authorization: Bearer <access_token>
```

- Токен живёт `expires_in` секунд — кэшируйте и обновляйте по истечении (или по `401`).
- `client_id`/`client_secret` для 1С выдаём мы (обмен секретом — разово, по защищённому каналу).
- Scope для приёма данных — `ingest`.

## 2. Приём истории заказов — `POST /api/ingest/order-lines`

Грейн записи: **строка документа** `(заказ × номенклатура)`. Шлём **плоско**
(денормализованно) — 1С соединяет данные на своей стороне.

```
POST /api/ingest/order-lines
Authorization: Bearer <token>
Content-Type: application/json

{
  "items": [
    {
      "order_guid":  "a1b2c3d4-0000-0000-0000-000000000001",
      "order_num":   "ЗП-0001234",
      "order_date":  "2026-03-14",
      "client_guid": "c0ffee00-0000-0000-0000-000000000abc",
      "client_name": "ООО Стройметалл",
      "niche":       "Строительство",
      "n1":          "01. Металлопрокат",
      "n2":          "01.02. Сортовой прокат",
      "n3":          "01.02.03. Арматура",
      "n4":          "Арматура А500С 12мм",
      "item_guid":   "f00d0000-0000-0000-0000-000000000def",
      "qty":         5.4
    }
  ]
}
```

### Поля

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `order_guid` | string (GUID) | да | идентичность заказа |
| `order_num` | string | да | отображение |
| `order_date` | string `YYYY-MM-DD` | нет | хронология |
| `client_guid` | string (GUID) | да | идентичность клиента |
| `client_name` | string | да | отображение |
| `niche` | string | да* | группировка по нише (без неё нет анализа по нише) |
| `n1`, `n2` | string \| null | нет | верхние уровни иерархии |
| `n3` | string | да | товарная подгруппа (анализ идёт на этом уровне) |
| `n4` | string | да | товар |
| `item_guid` | string (GUID) | да | идентичность товара (ключ к остаткам) |
| `qty` | number | да | количество, **в тоннах** |
| `deleted` | bool | нет | `true` → удалить этот заказ (см. ниже) |

### Семантика (важно)

- **Грейн обновления — документ-заказ.** Каждый `order_guid`, пришедший в пачке,
  **полностью заменяется**: сервис удаляет все прежние строки этого заказа и
  пишет присланные. Поэтому при изменении заказа шлите **его строки целиком**,
  а не одну изменённую строку.
- **Удаление/отмена заказа** — пришлите хотя бы одну запись с этим `order_guid`
  и `"deleted": true` (строки можно не передавать). Заказ будет удалён.
- **Идемпотентность** — повторная отправка той же пачки безопасна (тот же
  результат), ретраи не создают дублей.
- **Пачки** — разумный размер одной пачки 1 000–10 000 строк. Строки одного
  заказа должны быть **в одной пачке** (иначе частичная замена документа).

Ответ:
```json
{ "accepted": 1, "orders_affected": 1 }
```

## 3. Приём остатков — `POST /api/ingest/stock`

Ключ — `item_guid`. Шлите **только изменившиеся** остатки (как в п.4 вашего письма).

```
POST /api/ingest/stock
Authorization: Bearer <token>
Content-Type: application/json

{
  "items": [
    { "item_guid": "f00d0000-...-def", "n4_name": "Арматура А500С 12мм",
      "on_stock": 124.5, "in_transit": 30.0 }
  ]
}
```

| Поле | Тип | Назначение |
|---|---|---|
| `item_guid` | string (GUID) | ключ (upsert) |
| `n4_name` | string \| null | для сверки |
| `on_stock` | number \| null | остаток, тн |
| `in_transit` | number \| null | в пути, тн |

Семантика — **upsert по `item_guid`** (новые добавляются, существующие
обновляются). Ответ: `{ "accepted": N }`.

---

## 4. Пересчёт аналитики — `POST /api/ingest/refresh` (опционально)

Сервис пересобирает агрегаты **сам, по таймеру** (по умолчанию каждые ~10 мин),
так что после обычной заливки ничего звать не нужно. Если нужно форсировать
пересчёт сразу после большой пачки:

```
POST /api/ingest/refresh
Authorization: Bearer <token>
```

## 5. Анализ заявки — `POST /api/analyze` (для оператора)

Не часть приёма, но для полноты. **Без сохранения**: прислали черновик заявки —
получили рекомендации. Анализ идёт на уровне **N3**; из заявки нужны только товар
и количество.

```
POST /api/analyze
Authorization: Bearer <token c scope analyze>
Content-Type: application/json

{
  "client_guid": "c0ffee00-...-abc",
  "lines": [
    { "item_guid": "f00d0000-...-def", "qty": 5.4 }
  ]
}
```

- `item_guid` + `qty` достаточно (`n3` определяем сами по каталогу); можно слать `n3` напрямую.
- Ответ — JSON с двумя списками рекомендаций (`analysis1_forgotten`, `analysis2_niche`).
- Клиент/товары должны быть уже залиты через `/api/ingest/*`.

## 6. Ошибки, надёжность

- Коды: `200` — принято; `400` — некорректное тело; `401` — нет/просрочен токен;
  `403` — токен без нужного scope; `5xx` — ошибка сервиса (повторите с backoff).
- **Ретраи безопасны** (идемпотентность по GUID). Рекомендуется экспоненциальный backoff.
- Недоступность сервиса не должна ронять 1С — копите и досылайте.

## 7. Открытые вопросы к стороне 1С

1. **Ниша (`niche`)** — где живёт в 1С? Реквизит контрагента, отдельный
   классификатор, регистр сведений? Без неё анализ по нише невозможен. **Риск №1.**
2. **Иерархия N1–N4** — как получаете 4 уровня (папки `Номенклатура` по `Родитель`,
   классификатор, реквизиты)?
3. **Единица `qty`** — гарантируется передача **в тоннах**? Если базовая ЕИ иная —
   конверсия на вашей стороне.
4. **Полнота при изменении заказа** — подтвердите, что шлёте **весь заказ целиком**
   (для корректной замены документа).
5. **Удаления/отмены** — будете слать `deleted: true` по отменённым/распроведённым заказам?
6. **Какие документы** включать — только проведённые? исключаются возвраты?
7. **Частота push** — сразу при проведении заказа (тогда оператор видит свежий заказ
   почти мгновенно) или пачками по расписанию?
8. **Точечная отдача заказа по GUID** (на вашей стороне) — нужна, если оператору
   надо разобрать только что созданный заказ до того, как он приедет общим потоком.
