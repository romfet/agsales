# Контракт приёма истории (1С → сервис, push) — внутренний

Документ для команды 1С по загрузке истории. **Точный формат всех вызовов — в
`onec_api.md`** (канонично); здесь — семантика и договорённости.

Интеграция **read-only со стороны сервиса**. Идентичность по **GUID**: клиент →
`client_id`, подгруппа → `n3_id`, товар → `n4_id`. Заказ → `order_num`; ниша
(Отрасль) → `niche`. Наименования товара/подгруппы не передаются (1С резолвит по
GUID); `client_name` — опционально, для отображения. Транспорт — TLS, тела —
JSON UTF-8.

> Остатки в интеграции **не участвуют** — на рекомендации не влияют.

---

## 0. Что реализовать на стороне 1С

1. **Выгрузка истории** дельтой (новые/изменённые заказы; дельтой управляет 1С):
   `POST /api/ingest/order-lines` пачками, затем `POST /api/ingest/commit`.
2. **Получение токена** на `POST /api/auth/token` по выданному секрету; далее —
   `Authorization: Bearer <token>`.
3. **Вызов анализа** `POST /api/analyze` при разборе заявки оператором.

**Формат строки истории** — `onec_api.md §2`. Обязательны: `order_num`,
`client_id`, `n3_id`, `n4_id`, `niche`, `qty`. Опционально: `order_date`,
`client_name`.

**Подтвердить:**
- [ ] идентичность по **GUID** (`client_id`, `n3_id`, `n4_id` = `Ссылка` объектов
      1С); наименования — на стороне 1С;
- [ ] история — **дельта** (новые/изменённые), заказ по `order_num`, при изменении
      присылается **целиком** (все строки) — сервис заменяет позиции заказа;
- [ ] **возвраты/корректировки** — как приходят (отдельный документ / отрицательное
      `qty` / признак) и учитывать ли их в аналитике;
- [ ] источник поля **`niche`** (Отрасль) в 1С;
- [ ] единица **`qty`** — тоннаж;
- [ ] **отметки времени** создания и закрытия заказа (нужны для метрик эффекта);
- [ ] готовность получать токен на `/api/auth/token` (секрет — по защищённому каналу).

**Что НЕ нужно передавать:** остатки; номер/идентификатор заказа в `/api/analyze`.

---

## 1. Авторизация

`POST /api/auth/token` → JWT со scope. Далее — `Authorization: Bearer <token>`.
`client_id`/`client_secret` выдаёт сервис. Право `ingest` — для `/api/ingest/*`,
`analyze` — для `/api/analyze`. Нет/просрочен токен → `401`; без права → `403`.
Формат — `onec_api.md §1`.

> auth-`client_id` приложения **не путать** с `client_id` контрагента в данных.

---

## 2. История заказов — `POST /api/ingest/order-lines`

Грейн — строка заказа `(заказ × товар)`, плоско, идентичность по GUID. Семантика —
**дельта**: новые и изменённые заказы. Заказ обновляется **целиком** (все строки
одного `order_num` заменяют прежние; upsert по заказу). Пачка — 1 000–10 000 строк.
Загрузка идемпотентна. Формат — `onec_api.md §2`.

## 3. Финализация пачки — `POST /api/ingest/commit`

После загрузки пачек — пересобирает агрегаты (можно не звать: сервис пересобирает
и по таймеру). Формат — `onec_api.md §3`.

## 4. Анализ заявки — `POST /api/analyze` (scope `analyze`)

Клиент + текущие позиции заявки → рекомендации. Анализ на уровне N3. Номер самого
заказа не нужен (заявка не сохраняется). Формат — `onec_api.md §4`.

## 5. Ошибки и надёжность

- Коды: `200` ок; `400` некорректное тело / пустая заявка; `401` нет/просрочен
  токен; `403` без права; `5xx` — повтор с backoff.
- Ингест идемпотентен. Недоступность сервиса не должна ронять 1С.
