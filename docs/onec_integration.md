# Интеграция с 1С — обзор обмена (внутренний)

Внутренний обзорный документ. Точные форматы всех вызовов — в `onec_api.md`
(канонично); детали приёма истории — в `onec_ingest_contract.md`.

Интеграция **read-only со стороны сервиса**: 1С пушит данные, сервис в 1С ничего
не пишет. Идентичность — по **GUID** (`client_id` / `n3_id` / `n4_id`); заказ —
`order_num`; ниша (Отрасль) — строка `niche`. Наименования товара/подгруппы не
передаются — 1С резолвит их у себя.

---

## 1. Data-flow

```
ЭТАП 1 (история, дельта):
  1С ──POST /api/ingest/order-lines──▶ сервис ──▶ БД (сырьё) ──commit──▶ пересчёт агрегатов

ЭТАП 2 (анализ, реальное время):
  1С ──POST /api/analyze {клиент + позиции заявки}──▶ сервис ──▶ рекомендации в ответе
```

- **Этап 1** — 1С пушит **дельту** заказов (новые/изменённые; дельтой управляет
  1С) + `commit`. Сервис складывает сырьё и пересобирает агрегаты.
- **Этап 2** — оператор формирует заявку; 1С шлёт позиции на анализ и сразу
  получает рекомендации. Заявка не сохраняется.

Этапы независимы: анализ работает по последней загруженной истории.

---

## 2. Авторизация

Приложение запрашивает токен на `POST /api/auth/token` по `client_id` +
`client_secret` → получает подписанный сервером JWT (scope `ingest` / `analyze`) →
ходит с ним: `Authorization: Bearer <access_token>`. Формат — `onec_api.md §1`.

> auth-`client_id` приложения-интегратора **не путать** с `client_id` контрагента
> в данных.

---

## 3. Этап 1 — приём истории

Плоские строки заказов, идентичность по GUID, дельта (новые/изменённые) +
`commit`. Заказ обновляется целиком (все строки одного `order_num`). Точный формат
и поля — `onec_api.md §2`, семантика и договорённости — `onec_ingest_contract.md`.

---

## 4. Этап 2 — анализ заявки

Запрос: `client_id` + позиции заявки (`n4_id` или `n3_id` + `qty`). Ответ: два
блока рекомендаций (`analysis1_forgotten`, `analysis2_niche`), анализ на уровне
N3. Полный формат запроса/ответа и поля — `onec_api.md §4`.

Крайние случаи: неизвестный `client_id` → пустые списки (не ошибка); товар не из
истории → строка игнорируется (нельзя привязать к N3).

---

## 5. Открытые вопросы к стороне 1С

1. **Идентичность по GUID** — `client_id`/`n3_id`/`n4_id` = ссылки объектов 1С.
2. **Ниша (`niche`)** — где хранится в 1С (реквизит контрагента / классификатор).
   Без неё нет анализа по нише.
3. **Иерархия номенклатуры** — как формируются `n3_id` (подгруппа) и `n4_id` (товар).
4. **Единица `qty`** — гарантируется ли тоннаж.
5. **Состав документов** — какие заказы включаются; возвраты/корректировки.
6. **Отметки времени** — дата/время создания и закрытия заказа (нужны для метрик
   эффекта — см. `effect_metrics.md`).
