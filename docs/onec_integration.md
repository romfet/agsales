# Интеграция с 1С — data-flow и API-контракт

Верхнеуровневый документ для команды 1С: как устроен обмен и какие два вызова
участвуют. Детали приёма истории — в `docs/onec_ingest_contract.md`; справочник
по полям/ключам/нише — в `docs/onec_contract.md`.

Интеграция **read-only со стороны сервиса**: сервис не пишет в 1С. Данные идут
двумя независимыми путями.

---

## 1. Data-flow

```
        ┌──────────────────────── ЭТАП 1: история (дельта от 1С) ──────────────────────┐
        │                                                                               │
  1С ──POST /api/ingest/order-lines──▶ сервис ──▶ БД (сырьё) ──commit──▶ пересчёт агрегатов│
        └───────────────────────────────────────────────────────────────────────────────┘

        ┌──────────────────────── ЭТАП 2: анализ (в реальном времени) ─────────────────┐
        │                                                                               │
  оператор/1С ──POST /api/analyze {клиент + позиции заявки}──▶ сервис                    │
                                                               │ считает по агрегатам    │
                            ◀── JSON с рекомендациями ─────────┘                         │
        └───────────────────────────────────────────────────────────────────────────────┘
```

- **Этап 1 (история)** — 1С пушит **дельту** заказов (новые/изменённые; дельтой
  управляет 1С) + `commit`. Сервис складывает сырьё и пересобирает агрегаты. Удалений нет.
- **Этап 2 (live)** — оператор формирует заявку; 1С шлёт **позиции заявки** на анализ
  и сразу в ответе получает рекомендации. Без сохранения.

Этапы независимы: анализ работает по последней загруженной истории.
Остатки в интеграции не участвуют (на рекомендации не влияют).

---

## 2. Авторизация (общая для всех вызовов)

Стандартный процесс: приложение запрашивает токен по секрету на
`POST /api/auth/token` → получает подписанный сервером JWT (со scope `ingest`/
`analyze`) → ходит только с ним:
```
POST /api/auth/token   { "client_id": "...", "client_secret": "..." }
→ { "access_token": "<JWT>", "token_type": "bearer", "expires_in": 3600, "scope": "ingest" }

Далее:  Authorization: Bearer <access_token>
```
Подробно — в `onec_ingest_contract.md §1`.

## 3. ЭТАП 1 — приём истории (1С → сервис)

> ⚠️ **Зависит от вашего JSON.** Точная структура будет зафиксирована по
> образцу. Текущая форма — в `onec_ingest_contract.md §2`: плоские строки заказов
> (поля как в Excel-выгрузке + `client_id`), дельта (новые/изменённые) + `commit`; удалений нет.

---

## 4. ЭТАП 2 — анализ заявки (1С → сервис → 1С)

### 4.1. Запрос (что 1С передаёт нам)

```
POST /api/analyze
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "client_id": "c0ffee00-0000-0000-0000-000000000abc",
  "lines": [
    { "N4": "Труба профильная 40х20х2 Углерод.", "qty": 5.4 },
    { "N4": "Арматура ф 14 А500С", "qty": 2.0 }
  ]
}
```

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `client_id` | string | да | клиент, по чьей истории/нише считаем |
| `lines[]` | array | да | позиции текущей (черновой) заявки |
| `lines[].N4` | string | да* | товар (наименование); подгруппа N3 определяется сервисом |
| `lines[].N3` | string | да* | можно прислать подгруппу напрямую вместо N4 |
| `lines[].qty` | number | нет | количество; для проверки «взял меньше обычного» |

\* Достаточно `N4` **или** `N3` в строке. Анализ — на уровне **N3 (подгруппа)**.

### 4.2. Ответ (что мы возвращаем 1С)

```json
{
  "client_id": "c0ffee00-…-abc",
  "niche": "Строительство",
  "analysis1_forgotten": [ { … } ],
  "analysis2_niche":     [ { … } ]
}
```

**`analysis1_forgotten`** — «что клиент обычно берёт, но забыл в этой заявке»
(по собственной истории клиента). До 5 позиций, сорт по частоте.

| Поле | Тип | Смысл |
|---|---|---|
| `type` | string | `missing` (нет в заявке) \| `low_quantity` (взято меньше обычного) |
| `n3` | string | товарная подгруппа |
| `n4` | string\|null | товар (наименование) |
| `order_count` / `total_orders` | int | в скольких заказах клиента был / всего заказов |
| `frequency_pct` | number | частота, % (order_count/total_orders) |
| `avg_qty` | number | средний тоннаж в заказе |
| `current_qty` | number\|null | сколько в текущей заявке (для `low_quantity`) |
| `priority` | string | `high` \| `medium` |

**`analysis2_niche`** — «что берут клиенты той же ниши, а в заявке нет». До 5
позиций, сорт по частоте в нише.

| Поле | Тип | Смысл |
|---|---|---|
| `n3`, `n4` | string | подгруппа / товар (наименование) |
| `niche` | string | ниша клиента |
| `niche_pct` | number | % клиентов ниши, берущих этот товар |
| `client_count` / `total_clients` | int | сколько клиентов ниши берут / всего в нише |
| `order_count` / `total_orders` | int | заказов с товаром / всего заказов ниши |
| `frequency_pct` | number | частота в заказах ниши, % |
| `client_bought_before` | bool | брал ли этот клиент товар хоть раз |
| `avg_qty_per_client` | number | средний тоннаж на клиента ниши |
| `priority` | string | `high` \| `medium` |

### 4.3. Поведение и крайние случаи

- **Stateless** — заявка нигде не сохраняется.
- Неизвестный `client_id` → пустые списки (не ошибка).
- `N4` не из каталога (товар не встречался в истории) → строку нельзя привязать к N3,
  она игнорируется.
- Коды: `200` ок; `400` пустая заявка; `401/403` авторизация; `5xx` — повтор с backoff.

## 5. Зависимости от этапа 1 (что финализируем после вашего JSON)

1. **Идентичность.** `client_id` в `/api/analyze` совпадает с `client_id` из
   истории; товар — по `N4` (наименование). Точное имя поля `client_id`
   фиксируем по вашему JSON.
2. **Иерархия N3.** Привязка `N4 → N3` берётся из истории; если товар не
   встречался в истории, резолв/рекомендации по нему невозможны.
3. **Структура БД** — фиксируется по присланному JSON; на контракт `/api/analyze`
   это не влияет (форма ответа стабильна).

Уже закрыто: формат истории = Excel-выгрузка + `client_id` (заказ по `ЗаказНомер`,
товар по `N4`); ниша = `Отрасль`; иерархия = готовые колонки; единица количества не
важна; дата — одно поле; остатки в интеграции не участвуют.
