# Математика рекомендаций

Точное описание всех вычислений рекомендательного сервиса: агрегаты и две
аналитики. Документ — справочник; **источник истины в коде**:

| Что | Где |
|---|---|
| Сырьё | `shipment_lines` (рекомендации), `order_line_versions` (воронка) — `backend/db/migrations/0001_baseline.sql` |
| Агрегаты рекомендаций | матвью в `backend/db/migrations/0001_baseline.sql` |
| Витрина эффекта + `client_niche` | `backend/db/migrations/0002_effect_funnel_n3_and_client_niche.sql` |
| Правила рекомендаций | `backend/app/domain/analyzer.py` (чистые функции) |
| Сборка запроса/ответа | `backend/app/services.py`, чтение — `backend/app/repository.py` |

Все агрегаты **материализуются на синке** (пересбор — `/api/ingest/commit` или
воркер), в запросе `/api/analyze` ничего не считается «на лету» — только чтение.

> **ВАЖНО (Фаза 3): профили строятся из ОТГРУЗОК** (`shipment_lines`), а не заказов
> — рекомендуем по факту закупок. **Единица события — `shipment_id`** (реализованная
> отгрузка). Ниже, где написано «заказ / `order_num` / `nunique(order)`», сейчас
> читается **«отгрузка / `shipment_id`»**. Имена полей вывода `order_count` /
> `total_orders` **сохранены для контракта**, но считают отгрузки. Заказы
> (`order_lines`) используются отдельно — для версий/диффа/воронки эффекта.

## 0. Данные и грануляр

- Сырьё — строки заказов: `order_num, order_date, client_id, niche, n3_id, n4_id, qty`.
- Иерархия номенклатуры **N1 → N2 → N3 → N4**, где **N3 = подгруппа**, **N4 = товар (SKU)**.
- **Анализ идёт на уровне N3.** N4 несётся как «представитель» подгруппы (1С
  резолвит наименования по GUID).
- **«Частота» = доля заказов, содержащих позицию** (а не число строк).
- Ниша клиента = **мода** (самое частое значение `niche` по строкам клиента).
- `qty` — тонны, `numeric`, округление до 3 знаков.

Обозначения: `client` = `client_id`, `N3` = `n3_id`, `N4` = `n4_id`,
`order` = `order_num`. `nunique(order)` — число различных заказов.

---

## 1. Базовые размерности

### client_dim (одна строка на клиента)
```
niche(client)        = mode(niche)                   -- самая частая ниша клиента
total_orders(client) = nunique(order)                -- всего заказов клиента
```

### niche_dim (одна строка на нишу)
```
total_clients_in_niche(niche) = nunique(client)      -- клиентов в нише
total_orders_in_niche(niche)  = nunique(order)       -- заказов в нише
```

### client_niche (одна строка на клиента) — резолв ниши в `/analyze`
```
niche(client) = mode(niche) по строкам ЗАКАЗОВ ∪ ОТГРУЗОК клиента
```
Ниша берётся из объединения заказов и отгрузок, поэтому резолвится **даже до
появления отгрузок** у клиента (иначе анализ по нише молча отключался бы). Именно
этот матвью читает `get_client_niche`.

### products
`N4 → N3` (для резолва позиции черновика к подгруппе): `n3_id = max(n3_id) по n4_id`.
Строится из **заказов ∪ отгрузок** — чтобы резолвился и товар, который заказан, но
ещё не отгружён.

## 2. Профиль клиента на N3 — `client_profile_n3` (вход Аналитики 1)

Одна строка на `(client, N3)`. За заказ подгруппа считается **один раз**
(без задвоения по SKU).

```
order_count(client,N3) = nunique(order)              -- в скольких заказах клиента есть N3
total_qty(client,N3)   = Σ qty                       -- суммарный тоннаж N3 у клиента
total_orders           = total_orders(client)        -- из client_dim

frequency_pct(client,N3)     = round( order_count / total_orders * 100 , 1 )
avg_qty_per_order(client,N3) = round( total_qty  / order_count      , 3 )

rep_n4_id(client,N3) = argmax_{N4 ∈ N3} nunique(order с этим N4)     -- представитель
                       (при равенстве — меньший n4_id)
```
- `frequency_pct` — **как часто клиент берёт эту подгруппу** (доля его заказов).
- `avg_qty_per_order` — средний тоннаж подгруппы **в заказе, где она есть**.
- `rep_n4_id` — самый частый у клиента товар подгруппы (для отображения).

---

## 3. Нишевый профиль на N3 — `niche_profile_n3` (вход Аналитики 2)

Одна строка на `(niche, N3)`. Клиенты/заказы считаются **различными**.

```
client_count(niche,N3) = nunique(client)             -- сколько клиентов ниши берут N3
order_count(niche,N3)  = nunique(order)              -- в скольких заказах ниши есть N3
total_qty(niche,N3)    = Σ qty

niche_pct(niche,N3)      = round( client_count / total_clients_in_niche * 100 , 1 )
niche_freq_pct(niche,N3) = round( order_count  / total_orders_in_niche  * 100 , 1 )
avg_qty_per_client(niche,N3) = round( total_qty / client_count , 3 )

rep_n4_id(niche,N3) = argmax_{N4 ∈ N3} nunique(client с этим N4)     -- представитель
```
- `niche_pct` — **охват по клиентам**: доля клиентов ниши, берущих подгруппу.
- `niche_freq_pct` — **частота по заказам** ниши.
- Различие важно: **порог рекомендации — по `niche_pct`**, а **ранжирование — по
  `niche_freq_pct`** (см. §5).

> Флаг «клиент брал подгруппу ранее» (`client_bought_before` в Аналитике 2) —
> это `N3 ∈` множество подгрупп профиля клиента (`client_profile_n3`), без
> отдельного N4-профиля. Вход обеих аналитик — **N3-профили**.

## 4. Аналитика 1 — «Забытое» (`analyze_forgotten`)

Вопрос: *что клиент обычно берёт, но забыл/недобрал в текущей заявке.*

Индекс черновика: `order_n3` = множество N3 в заявке; `order_qty[N3]` = Σ qty по N3.

Для каждой строки `client_profile_n3`:

**A. Подгруппа отсутствует в заявке** (`N3 ∉ order_n3`):
```
если frequency_pct ≥ MIN_FREQUENCY_PCT (5):
    type = "missing"
    priority = "high"  если frequency_pct ≥ HIGH_FREQUENCY_PCT (10)
               "medium" иначе
    current_qty = null
```

**B. Подгруппа есть, но мало** (`N3 ∈ order_n3`):
```
current_qty = order_qty[N3]                      -- сумма по N3 в заявке
если avg_qty_per_order > 0 И current_qty < avg_qty_per_order * LOW_QTY_RATIO (0.5):
    type = "low_quantity"
    priority = "medium"
```
Иначе — не рекомендуем.

**Сортировка/срез:** по `frequency_pct` ↓, оставить **TOP_N = 5**.

Поля результата: `type, n3_id, n4_id(=rep), order_count, total_orders,
frequency_pct, avg_qty (=round(avg_qty_per_order,2)), current_qty, priority`.

---

## 5. Аналитика 2 — «Что берут в нише» (`analyze_niche`)

Вопрос: *что берут клиенты той же ниши, а в заявке этого нет.*

Ниша клиента — `niche(client)` из `client_niche` (мода по заказам ∪ отгрузкам).
Для каждой строки `niche_profile_n3` этой ниши:
```
если N3 ∉ order_n3 И niche_pct ≥ MIN_NICHE_PCT (5):
    рекомендуем
    priority = "high"  если niche_pct ≥ HIGH_NICHE_PCT (8)
               "medium" иначе
    client_bought_before = (N3 ∈ множество N3, которые клиент брал когда-либо)
```
**Сортировка/срез:** по `frequency_pct` ↓ (это поле = `niche_freq_pct`), **TOP_N = 5**.

Поля результата: `n3_id, n4_id(=rep), niche, niche_pct, client_count,
total_clients, order_count, total_orders(ниши), frequency_pct (=niche_freq_pct),
client_bought_before, avg_qty_per_client, priority`.

> **Дизайн (осознанно, унаследовано из легаси):** **фильтр — по `niche_pct`**
> (охват по клиентам), а **ранжирование и срез TOP-N — по `niche_freq_pct`**
> (частота по заказам). Это разные величины: подгруппа с высоким охватом, но
> низкой частотой по заказам может не попасть в TOP-N. Так было в исходном решении
> (`analyzer.py`, было `frequency_pct = niche_freq_pct` + сортировка по нему) —
> сохраняем совместимость. Отмечено в код-ревью как «мягкая» нестыковка — оставлено
> **намеренно**; менять на ранжирование по охвату только по решению бизнеса.

---

## 6. Константы (пороги) — `analyzer.py`

| Константа | Значение | Смысл |
|---|---|---|
| `MIN_FREQUENCY_PCT` | 5 | мин. частота клиента, чтобы счесть подгруппу «забытой» |
| `HIGH_FREQUENCY_PCT` | 10 | частота ≥ → приоритет `high` (Аналитика 1) |
| `LOW_QTY_RATIO` | 0.5 | «мало» = текущий тоннаж < средний × 0.5 |
| `MIN_NICHE_PCT` | 5 | мин. охват по нише, чтобы рекомендовать |
| `HIGH_NICHE_PCT` | 8 | охват ≥ → приоритет `high` (Аналитика 2) |
| `TOP_N` | 5 | сколько позиций возвращаем в каждой аналитике |

---

## 7. Конвейер запроса (`services.py`)

1. Позиции черновика нормализуются к N3: если пришёл `n4_id` — резолв через
   `products` (`N4 → N3`); можно прислать `n3_id` напрямую. Позиция без резолва в
   N3 — **игнорируется**.
2. `niche = niche(client)` (из `client_niche`); читаются `client_profile_n3` и
   `niche_profile_n3`.
3. Запускаются `analyze_forgotten` и (если есть ниша) `analyze_niche`.
4. Ответ: `{ client_id, niche, analysis1_forgotten[], analysis2_niche[] }`.

## 8. Пример (Аналитика 1)

Клиент сделал `total_orders = 20` заказов. Подгруппа «Арматура» (N3=A) встречалась
в `order_count = 8` заказах, суммарный тоннаж `total_qty = 96`.
```
frequency_pct     = 8/20*100 = 40.0
avg_qty_per_order = 96/8     = 12.0
```
- Если A **нет** в заявке: `40 ≥ 5` → `missing`, `40 ≥ 10` → `priority = high`.
- Если A **есть** и в заявке по ней `current_qty = 5`: `5 < 12*0.5 = 6` →
  `low_quantity` (взял меньше обычного).

## 10. Воронка эффекта — витрина `effect_funnel`

Отдельная от рекомендаций математика: **как заказ менялся и что реализовалось**.
Считается из **версий заказа** (`order_line_versions`) и **отгрузок**
(`shipment_lines`); наименования BI резолвит по GUID.

**Грануляр:** одна строка на `(order_id, N3)` — как и рекомендации, эффект меряется
на подгруппе (N4 сворачивается суммой). Единый грейн с журналом рекомендаций
позволяет считать прямой эффект джойном по `(order_id, n3_id)`.

**Состояния заказа** (по монотонному `version_seq` внутри заказа):
```
O (исходное)  = состав ПЕРВОЙ версии заказа   (version_seq = min)
F (финальное) = состав ПОСЛЕДНЕЙ версии заказа (version_seq = max)
```
> Допущение: **O = состав на момент рекомендации**. Оно верно, когда ассистента
> зовут при создании заявки (до правок) — что соответствует «заказ живёт ~2 дня,
> правки только пока открыт». Если правки были до консультации, `F−O` их тоже
> захватит.

**Меры (тоннаж), на `(order_id, N3)`:**
```
qty_original = Σ qty в O
qty_final    = Σ qty в F
qty_added    = max(qty_final − qty_original, 0)     -- прирост (вкл. рост существующей)
qty_shipped  = Σ qty отгрузок заказа по N3          -- фактически реализовано
```

**Флаги-счётчики позиций (0/1)** — считать число подгрупп в срезе:
```
is_original      = qty_original > 0
is_final         = qty_final > 0
is_new_position  = qty_original = 0 И qty_final > 0        -- подгруппы не было → появилась
is_qty_increased = qty_final > qty_original > 0            -- была и выросла
is_shipped       = qty_shipped > 0
```
> `qty_added` и `is_new_position` — про **разное**: `qty_added` — весь прирост
> тоннажа (в т.ч. рост существующей подгруппы), `is_new_position` — только факт
> появления новой подгруппы. Поэтому `Σ qty_added` ≠ тоннаж строк с
> `is_new_position=1` — это ожидаемо.

**Размерности строки:** `client_id`, `niche`, `period_month`.
```
period_month = первый день месяца ЗАКАЗА (по датам версий);
               дата отгрузки берётся, только если у заказа нет версий
               (заказ пришёл лишь через отгрузку).
```

**Воронка в BI:** `Σ qty_original → Σ qty_final → Σ qty_added → Σ qty_shipped`,
срез по `niche / N3 / period_month`.

**Атрибуция эффекта (собирается в BI):**
```
A (прямой)   = журнал ⨝ витрина по (order_id, n3_id): рекомендованное И добавленное/
               отгруженное. Матч на N3 (журнал и витрина — оба N3).
B (косвенный)= рост у «когорты с ассистентом» (есть запись в журнале) vs исключённых,
               по нерекомендованным позициям.
C (потенциал)= рекомендовано (журнал), но не добавлено/не отгружено (витрина).
```

## 11. Выгрузка витрины в BI — `/api/effect/*`

Read-only эндпоинты для загрузки данных в BI (право `effect`; пагинация
`limit`/`offset`). Отдают **GUID + меры**, имена BI подставляет из справочников 1С.

| Метод | Путь | Отдаёт |
|---|---|---|
| GET | `/api/effect/funnel` | строки `effect_funnel` (фильтры `niche`, `period_from`, `period_to`) |
| GET | `/api/effect/recommendations` | строки `recommendation_log` (`since_id` — инкрементально, `kind`) |

Ответ: `{ items: [...], limit, offset, count }`, где `count` — всего строк по
фильтру (для постраничной выгрузки). Журнал рекомендаций — append-only, поэтому BI
тянет инкрементально по `since_id` (id больше последнего загруженного).
