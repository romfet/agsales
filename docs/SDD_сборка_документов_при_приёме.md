## 1. Проблема

Сервис принимает данные 1С через `POST /api/ingest/order-lines` и `POST /api/ingest/shipments`.
Каждый запрос трактуется как **полное текущее состояние** каждого документа в нём: строки документа
(`order_id` / `shipment_id`) удаляются и заменяются пришедшими (`repository.py:139–227`).

Выгрузка 1С передаёт строки одного документа **в разных запросах** — фактически по одному товару
в каждом. Каждый следующий запрос затирает предыдущий, в БД остаётся последний присланный товар.

Факты (стенд А ГРУПП, 26.10.2026):

| Показатель | Значение |
|---|---|
| Документы с ≥ 2 разными товарами | РТУ: 403 из 123 917 (0,3 %); заказы: 776 из 302 583 (0,3 %) |
| Присылки заказа с одним товаром (`order_line_versions`) | 2 027 885 из ≈ 2 041 000 (99,4 %) |
| Заказы, у которых в истории было больше товаров, чем сейчас | 181 797 из 302 583 (60 %) |
| Заказ АГAG-133619 (11 позиций в 1С) | 22 запроса по 1–2 товара, два цикла выгрузки; в БД — 1 строка |
| Клиент СМС-РЕСУРС, отгрузки | 53 строки / 101 т в БД против 108 строк / 266 т в 1С |
| Запросов за 22–24.10 | `order-lines` ≈ 2,3 тыс., `shipments` 986 (≈ 125 РТУ на запрос) |

Последствия: рекомендации (`/api/analyze`) считаются по усечённым отгрузкам; метрики эффекта
(`effect_funnel`, `recommendation_effect_n4`) сравнивают «первую» и «последнюю» версии заказа,
которые на деле — случайные отдельные товары.

Контракт (`docs/onec_api.md` §2–3, `docs/Заказчик/Интеграция_с_1С.md` §3–4) требует передавать
заказ целиком, но не говорит явно «в одном запросе», рекомендует пачки по 1 000–10 000 строк, а
для отгрузок требования нет вовсе. Нарушение не обнаруживается и проходит молча.

## 2. Цели и не-цели

**Цели**

1. Если 1С передаёт в загрузке все строки документа — в любом числе запросов и в любом порядке —
   сервис собирает документ полностью.
2. Повтор пачки и повторная присылка документа в той же загрузке не задваивают тоннаж; при
   изменённом количестве действует последнее присланное.
3. Позиция, пропавшая из загрузки, **по умолчанию не удаляется** (нельзя отличить удаление в 1С от
   пропуска строки при выгрузке, §4.2). Удаление позиций — только в режиме, включаемом после
   подтверждения регламента выгрузки 1С, или по контрольным итогам документа (этап 2).
4. История версий заказа отражает изменения документа, а не нарезку выгрузки на запросы.
5. Подозрительные загрузки видны: сужение документа, уменьшение количества, неполные документы.
6. Восстановить уже испорченные данные: заказы — из истории, отгрузки — повторной загрузкой.
7. Формат запроса ingest для 1С не меняется; `/api/analyze` и математика не меняются.

**Не-цели**

- Построчные дельты в строгом смысле (1С присылает только изменённые строки документа) — §4.1, В1.
- Гарантия полноты без участия 1С: пропуск строки при постраничной выгрузке (§4.2) сервис
  обнаружить не может. Гарантию дают только контрольные итоги документа (этап 2) или выгрузка,
  не теряющая строк.
- Остатки, выручка, иные новые поля.

**Важно:** цель 3 означает, что до подтверждения регламента 1С удалённые в 1С позиции заказа
**остаются в данных сервиса** (и в метриках эффекта, §8). Это сознательная цена защиты от
потери данных; она снимается этапом 2 или режимом `replace` (§6.5).

## 3. Термины

- **Документ** — заказ (`order_id`) или РТУ (`shipment_id`).
- **Пачка** — один HTTP-запрос ingest (`items[]`).
- **Загрузка** — несобранные пачки одного вида (`kind` = `orders` | `shipments`) на момент сборки.
- **Сборка** — применение загрузки к боевым таблицам (§6.3).

## 4. Допущения о выгрузке 1С и их проверка

### 4.1. Документ в загрузке передаётся полностью

> В пределах одной загрузки 1С передаёт каждый затронутый документ полностью — все его строки,
> возможно в разных пачках.

Подтверждения: заказ АГAG-133619 в каждом из двух циклов пришёл всеми позициями; отгрузки за
22–24.10 пришли примерно по всем 124 тыс. РТУ. Если допущение неверно (1С шлёт только изменённые
строки), режим `keep` (§6.5) ничего не теряет, а режим `replace` удалил бы неизменённые строки —
поэтому `replace` включается только после ответа на В1.

Проверка на стенде — доля пар «заказ × цикл», где цикл содержит **все** товары заказа (цикл —
присылки без глобальной паузы > 2 ч; считается по distinct `version_seq`):

```sql
WITH seqs AS (
  SELECT version_seq, min(ingested_at) AS at FROM order_line_versions GROUP BY version_seq
), cyc AS (
  SELECT version_seq,
         sum(CASE WHEN at - lag(at) OVER (ORDER BY version_seq) > interval '2 hours'
                  THEN 1 ELSE 0 END) OVER (ORDER BY version_seq) AS cycle
  FROM seqs
), per AS (
  SELECT v.order_id, c.cycle, count(DISTINCT v.n4_id) AS n4_in_cycle
  FROM order_line_versions v JOIN cyc c USING (version_seq)
  GROUP BY v.order_id, c.cycle
), tot AS (
  SELECT order_id, count(DISTINCT n4_id) AS n4_total FROM order_line_versions GROUP BY order_id
)
SELECT p.cycle, count(*) AS order_cycles,
       count(*) FILTER (WHERE p.n4_in_cycle = t.n4_total) AS complete,
       round(100.0 * count(*) FILTER (WHERE p.n4_in_cycle = t.n4_total) / count(*), 1) AS complete_pct
FROM per p JOIN tot t USING (order_id)
WHERE t.n4_total > 1
GROUP BY p.cycle ORDER BY p.cycle;
```

Ограничение: версии пишутся только при смене `content_hash`, поэтому неизменённые однотоварные
заказы в циклах не видны — проверка отфильтрована на многотоварные (`n4_total > 1`).

### 4.2. Выгрузка не теряет строк

Если 1С листает выгрузку постранично по смещению (OFFSET) над живыми данными, вставка строки во
время выгрузки сдвигает страницы: одна строка приходит дважды, другая — **ни разу**. Пропуск
неотличим от удаления позиции. Поэтому позиции по умолчанию не удаляются (цель 3), а к 1С —
вопрос В6 (keyset-пагинация по ключу документа либо документ целиком в одной пачке).

### 4.3. Режим вызова `commit`

**Результат — §4.5: commit вызывается после каждой пачки.**

Если 1С вызывает `commit` посреди выгрузки (после каждой пачки или каждого задания), сборка по
commit работает с фрагментами. Поэтому до подтверждения «один commit в конце полной выгрузки»
(В3) commit-сборка тоже работает в режиме `keep`. Проверка по логам — частота и моменты commit
относительно пачек:

```bash
docker logs -t --since 148h agsales-api-1 2>&1 | grep -E "POST /api/ingest/(commit|order-lines|shipments)" \
  | awk '{print substr($1,1,16), $0 ~ /commit/ ? "COMMIT" : "batch"}' | uniq -c | head -100
```

### 4.4. Интервалы между пачками

Пороги автосборки (§6.4) выбираются по фактическим паузам:

```sql
WITH s AS (SELECT version_seq, min(ingested_at) at FROM order_line_versions GROUP BY 1),
g AS (SELECT at - lag(at) OVER (ORDER BY version_seq) AS gap FROM s)
SELECT width_bucket(extract(epoch FROM gap)/60, 0, 240, 12) AS bucket_20min, count(*)
FROM g WHERE gap IS NOT NULL GROUP BY 1 ORDER BY 1;
```

### 4.5. Результаты проверок на стенде (логи API за 148 ч, 26.10.2026)

Пачки `order-lines` + `shipments` по часам:

| Сеанс выгрузки | Пачек | `commit` | Темп |
|---|---|---|---|
| 22.10, 19:00 – 23.10, 00:xx (~5,5 ч) | 1 476 | **0** | до 466 пачек/ч |
| 23.10, 06:49 – 09:xx (~3 ч) | ≈ 45 | ≈ 39 | ≈ 1 пачка / 5 мин |
| 23.10, 20:00 – 24.10, 08:49 (~13 ч) | ≈ 1 850 | ≈ 1 815 | 130–167 пачек/ч |
| 24.10, 08:49 – 26.10 | 0 | 0 | — |

Выводы:

- **В3 — ответ получен: с 23.10 1С вызывает `commit` после каждой пачки** (по часам число commit
  совпадает с числом пачек: 167/167, 161/161, 155/155 …). 22.10 commit не вызывался вовсе.
  Значит, `commit` **не является** сигналом «загрузка закончена» и не может быть триггером сборки
  (§6.4).
- **Побочный эффект в текущей версии:** каждый `commit` синхронно пересчитывает все 10 матвью
  (`api/ingest.py:37–41`). Сеанс с commit шёл в ~3 раза медленнее (130–167 пачек/ч против 466) и
  растянулся на 13 часов — выгрузку тормозит наш синхронный пересчёт. Мера этапа 0 — §14.
- **В5 — ответ получен:** выгрузки ночные, 5,5–13 ч; внутри сеанса пачки идут каждые 8–30 с,
  между сеансами — паузы от 10 ч. Порог `idle` 30–60 мин сеанс не режет; порог `max_delay`
  меньше длительности сеанса (180 мин) **резал бы его** — увеличен (§6.4).
- **В1, В2 — по данным в основном подтверждены:** заказ АГAG-133619 (июнь) заново пришёл всеми
  позициями в двух ночных циклах — похоже на полную перевыгрузку истории с документом целиком
  по частям. Запрос §4.1 подтвердит это по всем многотоварным заказам.

## 5. Текущее поведение (as is)

```
POST /ingest/order-lines ─► DELETE order_lines WHERE order_id IN (пачка); INSERT строки пачки
                            INSERT order_line_versions (если content_hash ≠ последнего) ← версия на пачку
POST /ingest/shipments   ─► DELETE shipment_lines WHERE shipment_id IN (пачка); INSERT строки пачки
POST /ingest/commit      ─► refresh_aggregates() синхронно (worker — то же раз в REFRESH_INTERVAL_MINUTES)
```

Видимость: матвью — после ближайшего `refresh_aggregates` (до 10 мин); `/api/analyze` с периодом
читает `shipment_lines` напрямую (`repository.py:273–304, 348–447`) — сразу после записи.

## 6. Решение (to be)

```
POST /ingest/order-lines ─┐
POST /ingest/shipments   ─┴► ingest_batches + staging_* (ничего не удаляет, отвечает сразу)

POST /ingest/commit?kind= ─► отметка «запрошена сборка» (202, merge_id) ─┐
worker: пауза по kind ≥ IDLE  или  старейшая пачка ≥ MAX_DELAY ──────────┤
                                                                          ▼
                       worker: merge_staging(kind) — одна транзакция, xact advisory-lock
                       для каждого документа: по каждому n4 — строки из ПОСЛЕДНЕЙ пачки с этим n4
                       + правило сужения (keep/replace) → DELETE+INSERT в боевую таблицу
                       + версия заказа (§6.6)
                                                                          ▼
                                                               refresh_aggregates()
```

Режим `INGEST_MODE=staged|direct`; `direct` — текущее поведение (откат без релиза, §10.3).

### 6.1. Модель данных — миграция `0007_ingest_staging.sql`

```sql
-- Семантика order_line_versions.version_seq меняется: в режиме staged — одна версия на сборку
-- (комментарий в 0001 «на пачку загрузки» относится к режиму direct; 0001 не правим).
CREATE SEQUENCE IF NOT EXISTS ingest_batch_seq;

CREATE TABLE IF NOT EXISTS ingest_batches (
    batch_id      bigint PRIMARY KEY DEFAULT nextval('ingest_batch_seq'),
    kind          text NOT NULL CHECK (kind IN ('orders', 'shipments')),
    received_at   timestamptz NOT NULL DEFAULT now(),
    payload_hash  text NOT NULL,
    items         integer NOT NULL,
    merged_at     timestamptz,
    merge_id      bigint
);
CREATE INDEX IF NOT EXISTS ix_ingest_batches_pending
    ON ingest_batches (kind, batch_id) WHERE merged_at IS NULL;
CREATE UNIQUE INDEX IF NOT EXISTS ux_ingest_batches_pending_hash
    ON ingest_batches (kind, payload_hash) WHERE merged_at IS NULL;

CREATE TABLE IF NOT EXISTS staging_order_lines (
    batch_id bigint NOT NULL,
    order_id text NOT NULL, order_num text NOT NULL, order_date date,
    client_id text NOT NULL, client_name text, niche text,
    n3_id text NOT NULL, n4_id text NOT NULL, qty numeric NOT NULL,
    deleted boolean NOT NULL DEFAULT false
);
CREATE INDEX IF NOT EXISTS ix_staging_order_lines ON staging_order_lines (order_id, batch_id);
CREATE INDEX IF NOT EXISTS ix_staging_order_lines_batch ON staging_order_lines (batch_id);

CREATE TABLE IF NOT EXISTS staging_shipment_lines (
    batch_id bigint NOT NULL,
    shipment_id text NOT NULL, shipment_num text, shipment_date date,
    order_id text NOT NULL, client_id text NOT NULL, client_name text, niche text,
    n3_id text NOT NULL, n4_id text NOT NULL, qty numeric NOT NULL,
    deleted boolean NOT NULL DEFAULT false
);
CREATE INDEX IF NOT EXISTS ix_staging_shipment_lines ON staging_shipment_lines (shipment_id, batch_id);
CREATE INDEX IF NOT EXISTS ix_staging_shipment_lines_batch ON staging_shipment_lines (batch_id);

-- Последняя применённая пачка по товару документа (§6.3 п.7): поздно зафиксированная
-- старая пачка не перекрывает более новую.
CREATE TABLE IF NOT EXISTS staging_applied (
    kind     text NOT NULL,
    doc_id   text NOT NULL,               -- order_id | shipment_id
    n4_id    text NOT NULL,
    batch_id bigint NOT NULL,
    PRIMARY KEY (kind, doc_id, n4_id)
);

CREATE TABLE IF NOT EXISTS ingest_merges (
    merge_id     bigserial PRIMARY KEY,
    kind         text NOT NULL,
    requested_at timestamptz NOT NULL DEFAULT now(),
    trigger      text NOT NULL,            -- commit | idle | max_delay | recovery
    started_at   timestamptz,
    finished_at  timestamptz,
    shrink_mode  text,                     -- keep | replace
    batches integer, documents integer, lines integer,
    documents_shrunk integer,              -- документов, где пропали позиции (n4)
    documents_qty_decreased integer,       -- документов, где уменьшился тоннаж по n4
    positions_kept integer,                -- позиций, сохранённых правилом keep
    single_product_share numeric,          -- доля однотоварных документов в сборке
    error        text
);
```

Боевые таблицы и матвью не меняются. `db/tables.py` — Core-объекты новых таблиц.

### 6.2. Приём пачки (режим `staged`)

1. Пустой `items` → `{"accepted": 0, "status": "empty"}`, пачка не создаётся.
2. `payload_hash` = md5 канонизированного `items` (строки отсортированы, все поля).
3. `INSERT ingest_batches … ON CONFLICT (kind, payload_hash) WHERE merged_at IS NULL DO NOTHING`.
   Конфликт = повтор несобранной пачки → `status: "duplicate"`, `duplicate_of`. Повтор уже
   собранной пачки принимается как новая пачка: правило §6.3 делает его безвредным.
4. `INSERT staging_*` — все строки как пришли (включая `deleted`), в той же транзакции.
5. Ответ: `accepted` = число строк запроса (в т.ч. для повтора — чтобы 1С не считала это ошибкой),
   `batch_id`, `status` (`staged` | `duplicate` | `empty` | `applied` в режиме `direct`),
   `duplicate_of`, прежние `orders_affected` / `shipments_affected`.

Валидация (Pydantic) без изменений: невалидная пачка отклоняется целиком (422).

### 6.3. Сборка — `merge_staging(kind, trigger)`

Выполняется **только в worker** (не в HTTP-запросе), одна транзакция на `kind`, под
`pg_advisory_xact_lock(776611, kind_code)` — снимается при commit/rollback транзакции, не зависает на
соединении пула. `refresh_aggregates` (session-lock 776610 на своём соединении) вызывается после
фиксации транзакции сборки; отдельный ключ нужен, чтобы сборка и пересчёт агрегатов не ждали друг
друга без необходимости.

1. **Снимок.** Пачки `kind`, `merged_at IS NULL`, по возрастанию `batch_id` — явным списком.
   Пачка, транзакция которой зафиксируется позже, попадёт в следующую сборку.
2. **Состав документа по правилу «последняя пачка по товару».** Для каждого документа и каждого
   `n4_id`: берутся **все строки этого `n4_id` из пачки с наибольшим `batch_id`**, где он встречался
   (кратность внутри пачки сохраняется: 3,824 + 3,824 в одной пачке остаются двумя строками).
   Следствия: повтор страницы, ретрай, повторная присылка документа в той же загрузке и изменение
   количества дают «последнее присланное», а не сумму.
3. **`deleted: true`.** Строка удаления в пачке `k` означает «документ удалён на момент `k`»:
   все строки документа из пачек `< k` отбрасываются; строки из пачек `> k` образуют новый состав.
   Если после удаления строк нет — документ удаляется из боевой таблицы. К документу с удалением в
   загрузке правило `keep` **не применяется**. На флаг не опираемся: по контракту 1С удалений
   не шлёт (`docs/onec_api.md:39`); обработка сохраняется для совместимости с контрактом.
4. **Правило сужения** (§6.5) — сравнение собранного состава с текущим в БД **по мультимножеству
   строк каждого `n4_id`** (сумма `qty` и число строк), а не только по наличию `n4_id`.
5. **Применение:** `DELETE` документа + `INSERT` итогового состава.
6. **Версии заказов** — §6.6.
7. **Пачки старее уже применённого состава.** Если пачка с меньшим `batch_id` зафиксировалась после
   сборки более новой пачки того же документа, она попадает в следующую сборку; правило п.2
   применяется к объединению «строки этой загрузки» и **не перекрывает** `n4_id`, по которым в БД
   уже лежит более поздняя пачка. Для этого в боевых таблицах не храним `batch_id`, а ведём
   `staging_applied(kind, doc_id, n4_id, batch_id)` — последний применённый `batch_id` по товару
   документа (таблица в той же миграции; чистится по ретенции вместе с пачками).
8. `merged_at`, `merge_id` для снимка; строки staging снимка удаляются; итоги — в `ingest_merges`,
   лог `INFO` (и `WARNING` при `documents_shrunk` / `documents_qty_decreased` > 0).

Ошибка → откат, пачки несобраны, `ingest_merges.error`, лог `ERROR`; повтор на следующем тике.

Объём: полная загрузка заказов ≈ 2 млн строк staging, ≈ 300 тыс. документов. Сборка — SQL-операциями
над staging (оконные функции по `(doc_id, n4_id)`), без выгрузки в Python. Если замер (§11) покажет
недопустимую длительность одной транзакции — сборка порциями документов с идемпотентностью: порция
помечает свои документы в `staging_applied`, повторный запуск продолжает с непомеченных; версии
пишутся с одним `version_seq` на всю сборку (берётся до первой порции и хранится в `ingest_merges`).

### 6.4. Триггеры сборки

| Триггер | Условие | Кто |
|---|---|---|
| `idle` (основной) | нет новых пачек данного `kind` ≥ `INGEST_MERGE_IDLE_MINUTES` (по умолчанию 60) | worker, тик раз в минуту |
| `max_delay` (страховка) | старейшая несобранная пачка `kind` ≥ `INGEST_MERGE_MAX_DELAY_MINUTES` (по умолчанию 1440 = 24 ч, больше самого длинного сеанса — 13 ч) | worker |
| `commit` | **по умолчанию не запускает сборку** (`INGEST_MERGE_ON_COMMIT=false`): 1С вызывает commit после каждой пачки (§4.5), сборка по нему повторяла бы нарезку. `POST /api/ingest/commit` в `staged` отвечает сразу **202** и лишь отмечает время; включить сборку по commit можно, когда 1С будет вызывать его один раз в конце выгрузки (`?kind=orders\|shipments`) | api / worker |

Пауза и возраст считаются по `kind` отдельно, по `received_at` в той же транзакции, что снимок.
`POST /api/ingest/refresh` — только агрегаты (как сейчас). `GET /api/ingest/merges/{merge_id}` —
статус сборки (для `INGEST_MERGE_ON_COMMIT=true`).

`migrate` пачки не собирает (только `refresh_aggregates`, как сейчас).

### 6.5. Правило сужения

Сужение документа — в собранном составе по какому-то `n4_id` меньше строк или меньше `qty`, чем в БД,
либо `n4_id` из БД отсутствует.

| Настройка `INGEST_SHRINK_MODE` | Поведение |
|---|---|
| `keep` (по умолчанию для всех триггеров) | отсутствующие `n4_id` сохраняются из БД; уменьшение `qty` / числа строк по присланному `n4_id` **применяется** (это последнее присланное) и логируется; счётчики `positions_kept`, `documents_qty_decreased` |
| `replace` | документ заменяется собранным составом полностью; счётчик `documents_shrunk`; `WARNING` |
| `replace_on_commit` | `replace` только для сборок по `commit`, иначе `keep` (имеет смысл только при `INGEST_MERGE_ON_COMMIT=true` и commit один раз в конце выгрузки) |

`replace` / `replace_on_commit` включаются только после подтверждения В1, В3, В6. При контрольных
итогах документа (этап 2) `replace` применяется к документам, прошедшим сверку итогов, независимо от
настройки.

Поведение `keep` при замене товара в заказе (A → B): до подтверждения регламента — A + B. Влияние на
метрики эффекта — §8.

### 6.6. Версии заказов

- Версия пишется по **итоговому составу** документа после сборки (тому же, что в `order_lines`),
  если `content_hash` ≠ последней версии; один `version_seq` на сборку.
- `ingested_at` = `received_at` **самой ранней пачки загрузки**, где встретился заказ — иначе
  `recommendation_effect_n4` (`0006:44–50, 108`: `first_seen_at = min(ingested_at)`,
  `first_seen_at >= recommendation_at`) ошибочно сочтёт заказ, пришедший до рекомендации, новым.
- **Документ, разрезанный границей сборки** (часть товаров в сборке 1, остальные в сборке 2),
  иначе даст ложный эффект: вторая половина выглядит «добавленной» (`effect_funnel` first/last,
  `0002:35–50`; `same_order` `COALESCE(original.qty,0)=0`, `0006:73`). Правило: если предыдущая
  версия заказа создана сборкой по триггеру `idle`/`max_delay` не ранее
  `INGEST_VERSION_COALESCE_MINUTES` (по умолчанию 240) назад и новый состав — **надмножество**
  предыдущего (только добавлены `n4_id`), предыдущая версия **заменяется** (те же `version_seq` и
  `ingested_at`), а не добавляется новая.
- Цена правила: реальное добавление позиции менеджером в пределах окна после автосборки сольётся с
  исходной версией и не попадёт в эффект `same_order`. **Требует согласования с владельцем методики
  эффекта** (открытый вопрос О1, §13).

## 9. Восстановление данных

### 9.1. Заказы — из `order_line_versions` (без 1С)

Скрипт `python -m backend.sync.rebuild_orders_from_versions [--dry-run] [--gap-hours 2]`.
Запускать **в окне обслуживания при остановленном приёме** (`api` остановлен или 1С не выгружает),
под тем же advisory-lock, что сборка.

1. Только заказы, которые сейчас есть в `order_lines` (удалённые через `deleted` в версиях не
   отражены, `repository.py:146–151` — их не воскрешаем).
2. **Циклы — по каждому заказу отдельно:** новый цикл начинается, если (а) пауза между соседними
   версиями заказа > `--gap-hours`, или (б) в версии встретился `n4_id`, уже встречавшийся в текущем
   цикле (выгрузка отсортирована по номенклатуре — повтор товара = новый проход).
3. Состав цикла: для каждого `n4_id` — строки из последней версии цикла, где он встречался.
4. Пробел из-за дедупа версий (версия не пишется, если `content_hash` совпал с предыдущей,
   `repository.py:179`): `n4_id` из последней версии предыдущего цикла, совпадающий с первой
   версией текущего, переносится в текущий цикл.
5. Новая история: одна версия на заказ на цикл (дедуп по `content_hash`), `ingested_at` = первая
   присылка заказа в цикле.
6. `order_lines` = состав последнего цикла заказа.
7. Запись — **на месте**: старая история копируется `CREATE TABLE order_line_versions_raw_20261026
   AS SELECT * FROM order_line_versions`; затем в одной транзакции `DELETE` + `INSERT` в
   `order_line_versions` и `order_lines`; затем `refresh_aggregates`. (Переименовывать таблицу
   нельзя: `effect_funnel` и `recommendation_effect_n4` ссылаются на неё по OID и продолжили бы
   читать старую.)
8. `--dry-run`: отчёт без записи — заказов изменится, товаров добавится, распределение товаров на
   заказ до/после, число заказов, есть в версиях, но нет в `order_lines`.

Ограничения: позиция, удалённая из заказа внутри одного цикла, неотличима от разнесённой по пачкам
— останется; две строки одного `n4_id`, пришедшие разными запросами, схлопнутся в последнюю.
Перед запуском — `pg_dump` (стенд не резервируется).

### 9.2. Отгрузки — только повторной загрузкой

Истории РТУ нет. После включения `staged` — следующая плановая выгрузка (если полная) восстанавливает
РТУ; при `keep` усечённые позиции дополняются, не удаляясь. Если выгрузка — дельта, нужна разовая
полная перевыгрузка РТУ за период анализа (12 мес).

### 9.3. Проверка

Запросы 2, 3а, 12–15, Б из `sgsales/Проверка АГAG-251959 — SQL-сверка.md`. Критерии: СМС-РЕСУРС
≈ 266 т / 108 строк; доля однотоварных документов — порядка реальной. Дополнительно — сколько
клиентов сменили нишу (`client_niche` до и после) и как изменились итоги `effect_funnel`.

## 11. Тестирование

**Инфраструктура тестов**

- Фикстура: режим через monkeypatch настроек; очистка `ingest_batches`, `staging_*`,
  `staging_applied`, `ingest_merges` между тестами.
- `seed_mock.seed()`: после ingest — `merge_staging` для обоих `kind` (или принудительно `direct`),
  затем `refresh_aggregates`. Повторный `seed()` не должен упираться в `duplicate` — сид
  выполняется в чистой БД либо собирает сразу.
- Переписать под «сборка между загрузками» существующие тесты, закрепляющие «запрос = документ»:
  `test_order_versioning_and_diff` (`test_repository_integration.py:151–177`),
  `test_ingest_shipments_upsert_and_m2m` (179–198), тест эффекта N4 (314–345),
  `test_api_integration.py:104–108`. В режиме `direct` — оставить как есть (эталон).

**Новые сценарии (`staged`)**

1. Документ по одному товару в разных пачках → все товары (сценарий АГAG-133619).
2. Пачки в перемешанном порядке → тот же результат.
3. Повтор несобранной пачки → `duplicate`, `accepted` = N, тоннаж не задвоен; два одновременных
   повтора → одна пачка (уникальный индекс).
4. Повтор уже собранной пачки → следующая сборка, состав не меняется.
5. Тот же `n4_id` с другим `qty` в двух пачках → последнее `qty`.
6. Одинаковые строки одного товара в одной пачке → обе сохранены.
7. Одна страница пришла дважды среди других → без задвоения.
8. Позиция пропала из загрузки: `keep` → сохранена, `positions_kept`; `replace` → удалена,
   `documents_shrunk`; `replace_on_commit` → по триггеру.
9. Уменьшение `qty` по присланному `n4_id` → применено, `documents_qty_decreased`.
10. `deleted: true` в пачке k, строки до и после → состав = строки после k; `keep` не применяется.
11. Пачка зафиксирована во время сборки → в следующей сборке; более старая пачка не перекрывает
    более новую (`staging_applied`).
12. Триггеры: `idle` по `kind` отдельно, `max_delay` при непрерывном потоке, `commit?kind` — только
    свой `kind`; `/commit` → 202, `/merges/{id}`.
13. Версии: одна на сборку; `ingested_at` = первая пачка; заказ, пришедший до рекомендации и
    собранный после, не засчитывается `new_order`; разрез заказа границей автосборки → слияние
    версий (§6.6), `same_order` не даёт ложного эффекта.
14. Ошибка в середине сборки → откат, пачки несобраны, `ingest_merges.error`.
15. Параллельные commit-тик и idle-тик → одна сборка (xact-lock), без дедлока с `refresh_aggregates`.
16. `rebuild_orders_from_versions`: «22 версии по товару, два цикла» → два цикла, полный состав;
    повтор товара внутри паузы → новый цикл; пробел дедупа (§9.1 п.4); удалённый заказ не
    воскресает; `--dry-run` ничего не пишет; после записи `effect_funnel` читает новую историю.
17. `direct` ведёт себя как до изменения.

**Нагрузочный замер** на копии БД стенда: сборка полной загрузки заказов (~2 млн строк staging,
~300 тыс. документов) — длительность транзакции, пик памяти, рост WAL; по результату — решение о
сборке порциями (§6.3).

## 15. Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| Только требование к 1С «документ в одной пачке» | не защищает от повторения, ошибка снова пройдёт молча; остаётся рекомендацией в контракте |
| Объединение всех строк загрузки (v1 этого SDD) | задваивает `qty` при повторной присылке документа в загрузке, воскрешает удалённые позиции (ревью, §16) |
| Построчный upsert по `(документ, n4_id)` без загрузок | эквивалентен `keep` без сборки, но аналитика видит полусобранные документы, версии пишутся на каждую пачку |
| Контрольные итоги как единственная мера | требует доработки 1С; без неё не работает. Включены как этап 2 поверх сборки |
| Сборка синхронно в `/commit` | тайм-ауты у 1С / nginx при 2 млн строк |

**Отличия от текста SDD, найденные при реализации**

- §6.5: «устаревшая» загрузка — все присланные строки документа перекрыты более новыми в БД
  (§6.3 п.7) — документ **не сужает даже в режиме `replace`**. Без этого поздно зафиксированная
  старая пачка удаляла бы позиции, которых в ней нет (найдено мутационной проверкой).
- §6.4: commit-запросы, поступившие до сборки, закрываются ею (`_close_commit_requests`).
- §9.1 п.7: новая история пишется через UNLOGGED-таблицы `_rebuild_*` (в двух проходах:
  расчёт потоком, затем одна транзакция замены); сборка порциями (§6.3) не понадобилась
  на синтетике — решение по замеру на копии стенда.

**Тесты** (`backend/tests/test_ingest_staging_integration.py`, `test_rebuild_orders.py`;
локально 77 passed: 43 прежних + 34 новых): все сценарии §11, кроме нагрузочного замера, плюс
сквозной сценарий «выгрузка как у 1С» — моковая история (~1000 строк, ~480 заказов),
отсортированная по номенклатуре, страницы по 25 строк, commit после каждой: в `direct` усечён
каждый многотоварный заказ, в `staged` состав всех заказов и РТУ совпадает с эталоном. Мутационные
проверки (сломать правило «последняя пачка по товару», `keep`, слияние версий, `ingested_at`)
роняют соответствующие тесты. Живой прогон: `api` + `worker` в `staged`, четыре пачки по одному
товару → worker собрал РТУ из четырёх строк по таймеру и пересчитал агрегаты.

**Нагрузочный замер** (синтетика объёма стенда, без дампа: 300 тыс. заказов / 1,14 млн строк,
124 тыс. РТУ / 470 тыс. строк, пачки по 500 строк по номенклатуре; Postgres 16 в Docker,

Итог проверки: состав всех 300 тыс. заказов совпал с эталоном. Первый прогон выявил квадратичную
