# Интеграция с 1С — контракт обмена

Документ для команды 1С. Описывает обмен между 1С и сервисом аналитики продаж.
Обмен **read-only со стороны сервиса**: 1С передаёт данные, сервис в 1С ничего
не пишет.

Базовый адрес сервиса: `https://sgsales.rumsk01.keenetic.link`.
Все тела запросов и ответов — **JSON в кодировке UTF-8**, транспорт — **TLS**.

**Идентичность по GUID.** Клиент, отрасль, подгруппа, товар, заказ и отгрузка
идентифицируются по GUID (`client_id`, `niche`, `n3_id`, `n4_id`, `order_id`,
`shipment_id`) — наименования товара/подгруппы не передаются, 1С резолвит их у себя.
`order_num` / `shipment_num` — человекочитаемые номера (для отображения). **Ниша
(Отрасль) — тоже GUID.**

---

## 1. Обмен состоит из потоков

1. **История заказов** (`/api/ingest/order-lines`) — дельта заказов; заказ
   идентифицируется `order_id`. Сервис хранит **версии** заказа (историю
   состояний) для аналитики.
2. **Отгрузки** (`/api/ingest/shipments`) — факт отгруженного товара; отгрузка
   идентифицируется `shipment_id`, ссылается на заказ через `order_id`.
   **Рекомендации считаются по истории отгрузок**, поэтому этот поток обязателен.
3. **Анализ заявки** (`/api/analyze`) — в момент разбора заявки 1С передаёт клиента
   и текущие позиции, сразу получает рекомендации. Заявка не сохраняется.

Все вызовы, кроме получения токена и проверки доступности, требуют заголовок
`Authorization: Bearer <access_token>` (см. раздел 2).

| Метод | Путь | Право | Назначение |
|---|---|---|---|
| POST | `/api/auth/token` | — | получение токена |
| POST | `/api/ingest/order-lines` | `ingest` | загрузка заказов (дельта, версии) |
| POST | `/api/ingest/shipments` | `ingest` | загрузка отгрузок (факт) |
| POST | `/api/ingest/commit` | `ingest` | финализация загрузки |
| POST | `/api/analyze` | `analyze` | анализ заявки → рекомендации |
| GET | `/health` | — | проверка доступности |

---

## 2. Авторизация

1С запрашивает токен по выданным `client_id` и `client_secret`, затем передаёт
полученный токен в заголовке `Authorization` во всех последующих вызовах.

**Запрос:** `POST /api/auth/token` `{ "client_id": "onec", "client_secret": "<секрет>" }`
**Ответ:** `{ "access_token": "<JWT>", "token_type": "bearer", "expires_in": 3600, "scope": "ingest analyze" }`

- `client_id`/`client_secret` выдаёт сервис (по защищённому каналу); токен живёт
  `expires_in` секунд. Право `ingest` — для загрузки, `analyze` — для анализа.
- Нет/просрочен токен → `401`; токен без права → `403`.

> `client_id` приложения-интегратора (в авторизации) — это **не** `client_id`
> контрагента в данных.

---

## 3. Заказы — `POST /api/ingest/order-lines`

Единица данных — **строка заказа** `(заказ × товар)`, плоским списком. Ключ заказа —
**`order_id` (GUID)**. Семантика — **дельта**: новые и изменённые заказы. Заказ
обновляется **целиком**: все строки одного `order_id` передаются вместе и заменяют
прежние. **Присылайте заказ при каждом изменении** — сервис хранит версии (историю
состояний) для аналитики эффекта.

**Запрос:**
```json
{
  "items": [
    {
      "order_id":   "a1b2c3d4-e211-11ef-a380-3448edf7a2ad",
      "order_num":  "АГAG-212482",
      "order_date": "2024-08-11",
      "client_id":  "c0ffee00-4c57-11ec-a32e-3448edf7a2ad",
      "niche":      "f928c3fd-e211-11ef-a380-3448edf7a2ad",
      "n3_id":      "d24d39bd-1e9e-11ea-a969-0050569a475e",
      "n4_id":      "8917a4a0-1ea5-11ea-a969-0050569a475e",
      "qty":        1.032
    }
  ]
}
```

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `order_id` | string (GUID) | да | **ключ заказа** |
| `order_num` | string | да | номер заказа (отображение) |
| `client_id` | string (GUID) | да | клиент |
| `niche` | string (GUID) | да | отрасль (без неё нет анализа по нише) |
| `n3_id` | string (GUID) | да | подгруппа |
| `n4_id` | string (GUID) | да | товар |
| `qty` | number | да | количество |
| `order_date` | string `YYYY-MM-DD` (допустим ISO с временем) | нет | дата заказа |
| `client_name` | string | нет | наименование клиента (отображение) |
| `deleted` | bool | нет | `true` → удалить заказ по `order_id` |

Рекомендуемый размер пачки — 1 000–10 000 строк. Загрузка идемпотентна.
**Ответ:** `{ "accepted": 1, "orders_affected": 1 }`

---

## 4. Отгрузки — `POST /api/ingest/shipments`

Факт отгруженного товара. Контракт как у заказа + **`shipment_id` (ключ)** и
**`order_id` (ссылка на заказ)**. Заказ ↔ отгрузка — **многие-ко-многим** (заказ
может отгружаться несколькими отгрузками; отгрузка — покрывать несколько заказов;
связь на строке через `order_id`). Единица данных — строка `(отгрузка × товар)`.
Загрузка по `shipment_id` (перезалив заменяет строки этой отгрузки), удалений нет.
`qty` = **фактически отгружено**.

**Запрос:**
```json
{
  "items": [
    {
      "shipment_id":   "5e7ff0cd-e211-11ef-a380-3448edf7a2ad",
      "shipment_num":  "РТ-000123",
      "shipment_date": "2024-08-15",
      "order_id":      "a1b2c3d4-e211-11ef-a380-3448edf7a2ad",
      "client_id":     "c0ffee00-4c57-11ec-a32e-3448edf7a2ad",
      "niche":         "f928c3fd-e211-11ef-a380-3448edf7a2ad",
      "n3_id":         "d24d39bd-1e9e-11ea-a969-0050569a475e",
      "n4_id":         "8917a4a0-1ea5-11ea-a969-0050569a475e",
      "qty":           0.850
    }
  ]
}
```

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `shipment_id` | string (GUID) | да | **ключ отгрузки** |
| `order_id` | string (GUID) | да | ссылка на заказ (m2m) |
| `client_id` | string (GUID) | да | клиент |
| `niche` | string (GUID) | да | отрасль |
| `n3_id` | string (GUID) | да | подгруппа |
| `n4_id` | string (GUID) | да | товар |
| `qty` | number | да | фактически отгружено |
| `shipment_num` | string | нет | номер отгрузки (отображение) |
| `shipment_date` | string `YYYY-MM-DD` (допустим ISO с временем) | нет | дата отгрузки |
| `client_name` | string | нет | наименование клиента |
| `deleted` | bool | нет | удалить отгрузку по `shipment_id` |

**Ответ:** `{ "accepted": 1, "shipments_affected": 1 }`

---

## 5. Финализация загрузки — `POST /api/ingest/commit`

После загрузки пачек — пересобирает аналитику. **Ответ:** `{ "status": "ok", "rows": 26565 }`

## 6. Анализ заявки — `POST /api/analyze`

Передаётся клиент и текущие (черновые) позиции заявки; в ответе — рекомендации.
Анализ на уровне подгруппы (N3). Номер заказа не требуется — заявка не сохраняется.

**Запрос:**
```json
{
  "client_id": "c0ffee00-4c57-11ec-a32e-3448edf7a2ad",
  "lines": [ { "n4_id": "8917a4a0-1ea5-11ea-a969-0050569a475e", "qty": 1.5 } ]
}
```
В строке достаточно `n4_id` **или** `n3_id`, плюс `qty`.

**Ответ:**
```json
{
  "client_id": "c0ffee00-...-475e",
  "niche": "f928c3fd-e211-11ef-a380-3448edf7a2ad",
  "analysis1_forgotten": [
    { "type": "missing", "n3_id": "...", "n4_id": "...",
      "order_count": 8, "total_orders": 20, "frequency_pct": 40.0,
      "avg_qty": 12.5, "current_qty": null, "priority": "high" }
  ],
  "analysis2_niche": [
    { "n3_id": "...", "n4_id": "...", "niche": "f928c3fd-...",
      "niche_pct": 35.0, "client_count": 18, "total_clients": 51,
      "order_count": 120, "total_orders": 940, "frequency_pct": 12.8,
      "client_bought_before": false, "avg_qty_per_client": 9.3, "priority": "high" }
  ]
}
```

**`analysis1_forgotten`** — «что клиент обычно берёт, но не включил в заявку». До 5
позиций, сортировка по частоте. **`analysis2_niche`** — «что берут в той же
отрасли, а в заявке нет». До 5 позиций.

Счётчики `order_count`/`total_orders` считаются по **отгрузкам** клиента/отрасли
(имена полей сохранены для совместимости). `n3_id`/`n4_id` — подгруппа и
представительный товар (GUID); `niche` — GUID отрасли; `priority` — `high`/`medium`.

Крайние случаи: неизвестный `client_id` → пустые списки (не ошибка); товар, не
встречавшийся в истории, в резолве заявки игнорируется (пришлите `n3_id`).

---

## 7. Проверка доступности — `GET /health` → `{ "status": "ok" }`

## 8. Коды ответов
`200` ок; `400` некорректное тело / пустая заявка; `401` нет/просрочен токен;
`403` без права; `5xx` — повтор с задержкой. Формат ошибки: `{ "detail": "…" }`.

---

## 9. Что требуется подтвердить со стороны 1С

1. **GUID-ключи** — `order_id` (заказ), `shipment_id` (отгрузка), `client_id`,
   `niche` (Отрасль), `n3_id`, `n4_id` = ссылки объектов 1С (готовые GUID, без
   склеек на нашей стороне).
2. **Заказы — дельта с версиями:** присылать заказ **при каждом изменении** (целиком
   по `order_id`), чтобы сервис видел эволюцию состава.
3. **Отгрузки** — по `shipment_id`, со ссылкой `order_id`; связь заказ↔отгрузка
   **многие-ко-многим**; `qty` = фактически отгружено.
4. **Единица `qty`** — тонны.
5. **Состав документов** — какие заказы/отгрузки включаются; возвраты/корректировки
   (как представлены и учитывать ли).
6. **Отрасль (`niche`)** — источник GUID отрасли в 1С.
