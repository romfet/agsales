# Интеграция с 1С — контракт обмена

Документ для команды 1С. Описывает обмен между 1С и сервисом аналитики продаж.
Обмен **read-only со стороны сервиса**: 1С передаёт данные, сервис в 1С ничего
не пишет.

Базовый адрес сервиса: `https://sgsales.rumsk01.keenetic.link`.
Все тела запросов и ответов — **JSON в кодировке UTF-8**, транспорт — **TLS**.

**Идентичность по GUID.** Клиент, подгруппа и товар идентифицируются по GUID
(`client_id`, `n3_id`, `n4_id`) — наименования не передаются, 1С резолвит их у
себя по GUID. Заказ идентифицируется номером (`order_num`), отрасль (ниша) —
строкой (`niche`).

---

## 1. Обмен состоит из двух потоков

1. **История заказов** — 1С передаёт историю заказов дельтой (новые и изменённые
   заказы) и финализирует загрузку. Служит основой для аналитики.
2. **Анализ заявки** — в момент разбора заявки оператором 1С передаёт клиента и
   текущие позиции заявки и сразу получает рекомендации в ответе. Заявка нигде
   не сохраняется.

Потоки независимы. Анализ работает по последней загруженной истории.

Все вызовы, кроме получения токена и проверки доступности, требуют заголовок
`Authorization: Bearer <access_token>` (см. раздел 2).

| Метод | Путь | Право | Назначение |
|---|---|---|---|
| POST | `/api/auth/token` | — | получение токена |
| POST | `/api/ingest/order-lines` | `ingest` | загрузка истории заказов (дельта) |
| POST | `/api/ingest/commit` | `ingest` | финализация загрузки |
| POST | `/api/analyze` | `analyze` | анализ заявки → рекомендации |
| GET | `/health` | — | проверка доступности |

---

## 2. Авторизация

1С запрашивает токен по выданным `client_id` и `client_secret`, затем передаёт
полученный токен в заголовке `Authorization` во всех последующих вызовах.

**Запрос:**
```json
POST /api/auth/token
{ "client_id": "onec", "client_secret": "<секрет>" }
```
**Ответ:**
```json
{ "access_token": "<JWT>", "token_type": "bearer", "expires_in": 3600, "scope": "ingest analyze" }
```

- `client_id` и `client_secret` выдаёт сервис (передаются по защищённому каналу).
  Токен действует `expires_in` секунд.
- Право `ingest` — для загрузки истории, `analyze` — для анализа заявки.
- Отсутствие или истечение токена → `401`; токен без нужного права → `403`.

> `client_id` приложения-интегратора (в авторизации) — это **не** `client_id`
> контрагента в данных истории. Совпадение имени поля не означает совпадение
> сущностей.

---

## 3. Загрузка истории заказов — `POST /api/ingest/order-lines`

Единица данных — **строка заказа** `(заказ × товар)`, плоским списком.

Семантика — **дельта**: передаются новые и изменённые заказы (что уже передано и
что изменилось, отслеживает 1С). Заказ обновляется **целиком**: все строки одного
`order_num` передаются вместе и заменяют ранее загруженные строки этого заказа.

**Запрос:**
```json
{
  "items": [
    {
      "order_num":  "АГAG-212482",
      "order_date": "2024-08-11",
      "client_id":  "c0ffee00-0000-0000-0000-000000000012",
      "niche":      "04. Металлотрейдеры",
      "n3_id":      "a0a0a0a0-0000-0000-0000-0000000000n3",
      "n4_id":      "b0b0b0b0-0000-0000-0000-0000000000n4",
      "qty":        1.032
    }
  ]
}
```

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `order_num` | string | да | номер заказа (ключ заказа) |
| `client_id` | string (GUID) | да | клиент |
| `n3_id` | string (GUID) | да | подгруппа |
| `n4_id` | string (GUID) | да | товар |
| `niche` | string | да | отрасль клиента (без неё нет анализа по нише) |
| `qty` | number | да | количество |
| `order_date` | string `YYYY-MM-DD` | нет | дата заказа |
| `client_name` | string | нет | наименование клиента (для отображения) |
| `rec_source` | bool | нет | позиция добавлена из принятой рекомендации ИИ |
| `rec_kind` | string | нет | тип рекомендации: `forgotten` / `niche` |
| `rec_origin_order` | string | нет | `order_num`, где позиция была рекомендована |

Поля `rec_*` — **маркер рекомендации**: заполняются только для позиций,
добавленных из принятой рекомендации ИИ, и служат для расчёта эффекта ассистента
(см. документ по метрикам эффекта).

Рекомендуемый размер пачки — 1 000–10 000 строк. Загрузка идемпотентна.

**Ответ:** `{ "accepted": 1, "orders_affected": 1 }`

---

## 4. Финализация загрузки — `POST /api/ingest/commit`

Вызывается после загрузки пачек — пересобирает аналитику по актуальной истории.

**Ответ:** `{ "status": "ok", "rows": 26565 }`

---

## 5. Анализ заявки — `POST /api/analyze`

Передаётся клиент и текущие (черновые) позиции заявки; в ответе — рекомендации.
Анализ ведётся на уровне подгруппы (N3). Номер самого заказа не требуется —
заявка не сохраняется.

**Запрос:**
```json
{
  "client_id": "c0ffee00-0000-0000-0000-000000000012",
  "lines": [
    { "n4_id": "b0b0b0b0-0000-0000-0000-0000000000n4", "qty": 1.5 }
  ]
}
```
В строке достаточно передать `n4_id` **или** `n3_id`, а также `qty`.

**Ответ:**
```json
{
  "client_id": "c0ffee00-0000-0000-0000-000000000012",
  "niche": "04. Металлотрейдеры",
  "analysis1_forgotten": [
    { "type": "missing", "n3_id": "...", "n4_id": "...",
      "order_count": 8, "total_orders": 20, "frequency_pct": 40.0,
      "avg_qty": 12.5, "current_qty": null, "priority": "high" }
  ],
  "analysis2_niche": [
    { "n3_id": "...", "n4_id": "...", "niche": "04. Металлотрейдеры",
      "niche_pct": 35.0, "client_count": 18, "total_clients": 51,
      "order_count": 120, "total_orders": 940, "frequency_pct": 12.8,
      "client_bought_before": false, "avg_qty_per_client": 9.3, "priority": "high" }
  ]
}
```

**`analysis1_forgotten`** — «что клиент обычно берёт, но не включил в эту заявку»
(по собственной истории клиента). До 5 позиций, сортировка по частоте.

| Поле | Смысл |
|---|---|
| `type` | `missing` (нет в заявке) / `low_quantity` (взято меньше обычного) |
| `n3_id`, `n4_id` | подгруппа и товар (GUID) |
| `order_count`, `total_orders` | в скольких заказах клиента встречался / всего заказов |
| `frequency_pct` | частота, % |
| `avg_qty` | средний тоннаж в заказе |
| `current_qty` | количество в текущей заявке (для `low_quantity`) |
| `priority` | `high` / `medium` |

**`analysis2_niche`** — «что берут клиенты той же отрасли, а в заявке нет». До 5
позиций, сортировка по частоте в отрасли.

| Поле | Смысл |
|---|---|
| `n3_id`, `n4_id` | подгруппа и товар (GUID) |
| `niche` | отрасль клиента |
| `niche_pct` | доля клиентов отрасли, берущих этот товар, % |
| `client_count`, `total_clients` | клиентов отрасли берут / всего в отрасли |
| `order_count`, `total_orders` | заказов с товаром / всего заказов отрасли |
| `frequency_pct` | частота в заказах отрасли, % |
| `client_bought_before` | брал ли этот клиент товар ранее |
| `avg_qty_per_client` | средний тоннаж на клиента отрасли |
| `priority` | `high` / `medium` |

Поведение и крайние случаи:
- Неизвестный `client_id` → пустые списки (не ошибка).
- Товар, не встречавшийся в истории, не может быть привязан к подгруппе — такая
  строка заявки игнорируется.

---

## 6. Проверка доступности — `GET /health`

**Ответ:** `{ "status": "ok" }`

---

## 7. Коды ответов

- `200` — успех.
- `400` — некорректное тело / пустая заявка.
- `401` — отсутствует или истёк токен.
- `403` — токен без нужного права.
- `5xx` — временная ошибка сервиса; повтор с задержкой (backoff).

Формат ошибки: `{ "detail": "<описание>" }`.

---

## 8. Что требуется подтвердить со стороны 1С

1. **Идентичность по GUID** для клиента, подгруппы, товара — что передаются
   именно ссылки объектов 1С, а не наименования.
2. **Отрасль (ниша).** Где хранится в 1С (реквизит контрагента, отдельный
   классификатор, иное). Без отрасли анализ по нише невозможен.
3. **Иерархия номенклатуры** — как формируются подгруппа (`n3_id`) и товар
   (`n4_id`).
4. **Единица измерения количества** — гарантируется ли передача в тоннах.
5. **Состав документов** — какие заказы включаются в историю (проведённые;
   исключение возвратов/отмен; фильтр по организации/складу).
6. **Возвраты и корректировки** — как представлены в дельте (отдельный документ /
   отрицательное количество / признак) и учитывать ли их в аналитике.
7. **Отметки времени** — дата и, при необходимости, время создания и закрытия
   заказа (см. документ по метрикам эффекта).
8. **Маркер рекомендации** — готовность проставлять `rec_source` / `rec_kind` /
   `rec_origin_order` на строке заказа при принятии рекомендации ИИ (основа
   расчёта эффекта ассистента).
